# Agent Operational & Onboarding Guide (AGENTS.md)

Welcome, AI Agent! This document defines the operational boundaries, design patterns, testing strategies, and collaborative conventions for the `libCharon` repository.

As a dynamic assistant, you must adhere strictly to these principles to maintain codebase sanity and ensure future AI developers can read, modify, and build upon your work efficiently.

---

## 1. SaaS Context, Sibling Services & AI Skill Discovery

**libCharon** is a high-performance Python package/file utility library integrated within **Cura Cloud API** (`stardust-cura_cloud_api`). It handles reading, writing, and parsing of 3D print file packages, particularly:
- **G-Code Files** (`GCodeFile`, `GCodeGzFile`) and socket streaming protocols (`GCodeSocket`).
- **Open Packaging Convention (OPC)** containers.
- **UltiMaker Format Package (UFP)** bundles.

It provides a virtual file interface that allows the slicing/cloud platform to process print-ready packages dynamically without relying on absolute local path assumptions.

### 🔗 Sibling Services & Architecture Boundaries
`libCharon` is managed as a git submodule inside `stardust-cura_cloud_api`. To understand the wider ecosystem, refer to these sibling directories and their guidelines:
- **`stardust-cura_cloud_api`** (Parent repository): Located at relative path `../../` (the parent of `lib/libCharon`). Serves as the central backend resolver for slicing profiles, print options, and C++-based settings mapping.
- **`stardust-digitalfactory`**: Located at relative path `../../stardust-digitalfactory` from the atlas orchestration layer. Serves as the web portal and backend API gateway.
- **`stardust-commons`**: Located at relative path `../../stardust-commons` from the atlas orchestration layer. Provides low-level cloud client APIs and OAuth token processing.

## 2. Work Tracking, Git & Pull Request Habits

- **Jira Tracking**: All changes require an active Jira ticket starting with project key **`UC`** (Cloud / Stardust services, e.g., `UC-3697`) or **`NP`** (Cura Cloud services, e.g., `NP-1234`).
- **Git Commits & PR Titles**:
  - **No Semantic Prefixes**: Do **NOT** use conventional/semantic commit prefix tags (such as `feat:`, `fix:`, `chore:`, `refactor:`, etc.) in commit titles or Pull Request titles.
  - **Bracketed Ticket Prefix**: Every Git commit title and GitHub Pull Request title **MUST** start with the bracketed Jira key: `[UC-3697] <Descriptive Title>`.
  - **Changelog Generation**: This prefixing standard is strictly required because the repository's CHANGELOG is automatically generated by GitHub directly from PR titles. We do **NOT** use or maintain a local `CHANGELOG.md` file.
  - Commit message format:

    ```
    [UC-3697] Add custom pre-commit checks and Copilot guidelines

    Integrated Python code checkers, Talisman secret scanner, and Copilot role instructions.

    Contributes to UC-3697
    ```

- **PR Guidelines**:
  - Always open PRs as **DRAFT** state. Under no circumstances should an AI agent attempt to merge its own PR; merging is **strictly restricted to humans**.
  - Monitor CI status checks. Ensure style, formatting, mypy, and unit tests pass.
  - Append an empty human checklist for the review stage at the bottom of the PR description.

### 📝 Draft Pull Request Checklist

Ensure this empty checklist is appended to the bottom of your PR description:

```markdown
- [ ] **Developer V&V**: Python test suite (`pytest`) runs and passes completely.
- [ ] **Static Compliance**: `mypy`, `black`, and `flake8` static checks run with zero errors.
- [ ] **Architecture Check**: File footprints are kept compact (around 300 lines; max 400 lines).
```

### 📢 Standard PR Annotations & Alert Patterns

Always annotate pull request and merge descriptions with standard GitHub markdown alerts:

- **`> [!NOTE]`**: Useful information that users should know, even when skimming.
- **`> [!TIP]`**: Helpful advice for doing things better or more easily.
- **`> [!IMPORTANT]`**: Key information users need to know to achieve their goal.
- **`> [!WARNING]`**: Urgent info that needs immediate user attention to avoid problems.
- **`> [!CAUTION]`**: Advises about risks or negative outcomes of certain actions.

## 3. Directory Organization & Quality Control

### Core Directory Maps:
- `/Charon/`: Core library package.
  - `/Charon/Client/`: Client implementations for interacting with Charon interfaces.
  - `/Charon/Service/`: DBus-service interfaces and packaging daemons.
  - `/Charon/filetypes/`: Specialized file type handlers (`GCodeFile.py`, `OpenPackagingConvention.py`).
- `/tests/`: Automated unit tests using pytest.
- `/docs/`: API and developer documentation.
- `/service/`: Configuration and system files for systemd and dbus.

### 🧪 Automated Quality Control & Testing

We maintain a rigorous quality gate locally via wrapper scripts:

1. **Running Unit Tests (pytest)**:
   ```bash
   ./run_pytest.sh
   # Or run via python directly:
   pytest tests/
   ```
2. **Running Mypy Type Checking**:
   ```bash
   ./run_mypy.sh
   ```
3. **Running Style Analysis**:
   ```bash
   ./run_style_analysis.sh
   ```
4. **Dead Code and Complexity Checks**:
   ```bash
   ./run_dead_code_analysis.sh
   ./run_complexity_analysis.sh
   ```
5. **Run All Checks**:
   ```bash
   ./run_all_tests.sh
   ```

## 4. Designing for Future AI Generated Code

- **Decomposed File Footprints**: Keep individual Python modules as small as possible. Python files should ideally remain **around 300 lines (max 400 lines)** to minimize token overhead and keep context-windows clean.
- **Self-Documenting Code**: Write precise docstrings (PEP 257) and type hints instead of lengthy inline comments. Ensure every function signature is strictly typed.
- **Experimental Guardrails**: Never commit manual tests, scratch code, prototyping scripts, or draft outputs. Prototyping and experiments must reside exclusively inside the gitignored `scratch/` folder at the root of the repository.

## 5. Pre-commit Automation & Credentials Safety

This repository enforces automated quality checks using `pre-commit` before any git commit is recorded.

### Setup and Manual Use:
1. **Installation**: Ensure `pre-commit` is installed and set up locally:
   ```bash
   pip install pre-commit
   pre-commit install --hook-type pre-commit --hook-type commit-msg
   ```
2. **Manual Execution**: Run checks manually on all files:
   ```bash
   pre-commit run --all-files
   ```

### 🔐 Resolving Talisman Checksum Errors

When modifying files with custom structures or formatted expressions, Talisman may flag false-positive secrets:

1. Locate the file's target checksum from the Talisman pre-commit terminal report.
2. Open `.talismanrc` at the repository root and append or update the target ignore configuration block:
   ```yaml
   - filename: path/to/your/file.py
     checksum: [your_generated_sha256_hash]
   ```
